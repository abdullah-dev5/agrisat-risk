# Architecture

AgriSat Risk is a parametric crop-risk platform for agricultural lenders and insurers, MVP-scoped to wheat monitoring in Matiari District, Sindh. It is **decision-support only** — it never issues automated payouts.

## System overview

```
┌─────────────┐        HTTPS/JSON         ┌──────────────────────────┐
│  React SPA   │ ────────────────────────▶ │   FastAPI backend         │
│ (Vite build, │ ◀──────────────────────── │   (Gunicorn + Uvicorn)    │
│  static host)│      Supabase JWT          │                           │
└─────┬───────┘                            │  routes → services →      │
      │  Supabase Auth (login/session)      │  Supabase / GEE / models │
      ▼                                     └──────┬────────┬──────────┘
┌─────────────┐                                    │        │
│  Supabase    │◀───────────────────────────────────┘        │
│  Postgres +  │        service-role key (bypasses RLS)       │
│  PostGIS +   │                                              ▼
│  Auth + RLS  │                                   ┌───────────────────┐
└─────────────┘                                    │ Google Earth Engine│
                                                    │ (Sentinel-1/2,     │
                                                    │  CHIRPS rainfall)  │
                                                    └───────────────────┘
```

The backend also loads two local model artifacts in-process: a PyTorch super-resolution model (SEN2SR, `backend/models/sen2sr/model.pt`) and a scikit-learn gradient-boosted classifier (ML risk layer, `backend/models/ml_risk/model.joblib`).

Only the backend is containerized (`backend/Dockerfile`, root `docker-compose.yml`); the frontend is a static Vite build meant to be deployed to a CDN separately (see `docs/PRODUCTION.md`).

## Module map (M0–M12)

The project was delivered as a sequence of modules against an internal SRS. Full acceptance criteria live in `docs/MODULE-PLAN.md`; summary:

| # | Module | What it does |

| M1 | Auth & institutions | Institution registration, admin invites, JWT (JWKS + legacy HS256), tenant isolation |
| M2 | Field registration | Draw AOI on map or upload GeoJSON, metadata, area validation |
| M3 | Tier 3 pipeline | Sentinel-1 SAR + Sentinel-2 + CHIRPS via GEE — the always-available baseline tier |
| M4 | Tier 2 pipeline | Local SEN2SR super-resolution over GEE reflectance patches, with a GEE weekly-composite fallback |
| M5 | Tier 1 pipeline (PlanetScope) | **Deferred** — stubbed, blocked on E&R Program license |
| M6 | Fusion & storage | Tier-selection logic and time-series persistence |
| M7 | Baseline engine | District-level multi-year GEE statistics |
| M8 | Risk scoring | Z-score risk tiers, rainfall cross-check, audit trail |

Post-plan additions: live GEE field imagery previews, async job queue with `/fields/{id}/processing` polling, and the in-app `/guide` page.

## Field-processing data flow

1. **Register** (`POST /fields`) or **reprocess** (`POST /fields/{id}/reprocess`) validates the request, persists the field row, and enqueues a background job — the HTTP call returns immediately.
2. **Async job** (`backend/app/services/job_runner.py`) runs on a process-local `ThreadPoolExecutor(max_workers=2)`. It calls `field_service.process_field`, which:
   - fetches Tier 3 GEE data (and Tier 2 SEN2SR when enabled) via `services/tiers/*`,
   - fuses tiers in `services/fusion.py`,
   - loads or builds the district baseline (`services/baseline.py`),
   - computes a z-score risk tier with rainfall cross-check (`services/risk_engine.py`),
   - optionally elevates the tier using the ML classifier (`services/ml_risk.py`) when confidence ≥ `ML_RISK_CONFIDENCE_MIN`,
   - persists vegetation readings and the risk assessment (with audit trail).
3. The frontend polls `GET /fields/{id}/processing` (`frontend/src/hooks/useFieldProcessing.ts`, every 3s, up to 6 minutes) and updates the UI once the job reaches `ready`/`failed`.
4. Field imagery (RGB/NDVI thumbnails) is fetched on demand (`GET /fields/{id}/imagery`), generated by GEE and cached in-process for 10 minutes.

## Tenant isolation

Multi-tenant separation ("institution" = tenant) is enforced **at the application layer**, not by Postgres RLS at runtime:

- The backend always talks to Supabase using the **service-role key** (`core/supabase_client.py`), which bypasses Postgres RLS entirely.
- Every service function that reads or writes tenant data explicitly filters `.eq("institution_id", institution_id)` — confirmed consistently across `field_service.py` and `report_service.py`. There is no known instance of a missing filter today.
- Postgres RLS policies **do exist** in `supabase/migrations/001_initial_schema.sql` (an `auth_institution_id()` helper plus per-table policies) and would matter if a client ever queried Postgres directly with a user-scoped (anon/authenticated) key — but the frontend only uses Supabase directly for **auth**, never for direct table queries (`frontend/src/lib/supabase.ts`, `lib/auth.ts`). So today, RLS is a defense-in-depth safety net that isn't actually exercised by any request path.
- Practical implication: a missing `.eq("institution_id", …)` in any *new* service function would be a full cross-tenant data leak with no second layer of defense at request time. `scripts/verify_rls.py` re-validates this by testing cross-tenant isolation against the live API — treat it as a required check before shipping any change that touches field/report data access.

## Known limitations

- **Job queue is single-process only.** `job_runner.py`'s `ThreadPoolExecutor`-based queue now recovers from its own crashes (a background sweep marks fields stuck in `processing` past a timeout as `failed`, since 2026-09-27 — see `docs/AUDIT-FINDINGS.md` #2), but it still doesn't dedupe across multiple backend replicas. Horizontal scaling still needs a durable queue (Redis/etc.) per `docs/PRODUCTION.md`.
- **Google Earth Engine's free tier is noncommercial-only.** The entire Tier 3 pipeline runs on GEE, which is free today because the project has no paying customer yet — GEE's noncommercial terms explicitly prohibit fee-for-service use. This needs a paid Earth Engine commercial account (or a migration to the Copernicus Data Space Ecosystem) before any institution is billed for a AgriSat output. See [`docs/FREE-VS-PAID-RESOURCES.md`](FREE-VS-PAID-RESOURCES.md).

- **Automated tests cover logic, not integration.** `backend/tests/` (pytest) and `frontend/src/**/*.test.{ts,tsx}` (Vitest) run in CI on every push/PR, but both are unit-level against mocked/faked dependencies — nothing exercises a real Supabase call or a real GEE fetch end-to-end. The manual scripts (`scripts/verify_supabase.py`, `verify_rls.py`, `verify_gee.py`, `test_e2e_flows.py`) are still the way to check that; see `CONTRIBUTING.md`.

For the full, prioritized list of known issues and improvement ideas, see [`docs/AUDIT-FINDINGS.md`](AUDIT-FINDINGS.md).
